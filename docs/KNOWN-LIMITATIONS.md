# القيود المعروفة

## قيود تمنع البيع
- تطبيق WPF يحتوي على Ribbon Office-like قابل للطي، وشاشات مبيعات ومشتريات RTL متصلة بالـ API. المشتريات تشمل الموردين ومسودات فواتير الشراء، حساب VAT داخليًا وتقرير البنود وترحيل قيد GL مزدوج مربوط بالمصدر، مع اختيار المستخدم ما إذا كانت VAT تُفصل في أصل أم تبقى ضمن تكلفة الشراء. موفر OIDC غير مهيأ/غير مختبر حيًا، وبقية الشاشات والتشغيل التجاري ما زالت غير مكتملة.
- المبيعات تشمل العملاء ومسودات داخلية يمكن تصنيفها ضريبيًا وحفظ حسابها ثم ترحيل أثرها إلى GL بقيد متوازن ومربوط بالمصدر. وحدة WPF للصناديق والبنوك تدعم سندات القبض والصرف مع تخصيصها على الفواتير المرحلة وترحيلها إلى GL. توجد تقارير أعمار الذمم المدينة والدائنة حتى تاريخ محدد؛ تعتمد على تاريخ القيد المرحلة والتسويات المرحلة فقط وتحتاج مطابقة مستقلة مع الأستاذ العام. لا توجد فاتورة ضريبية/مبسطة قانونية صادرة أو تكامل ZATCA أو إشعارات دائنة/مدينة أو تسوية بنكية.
- لا تكامل ZATCA/FATOORA مثبت ولا XML/توقيع/تجزئة/QR ولا قبول sandbox.
- الاشتراكات للقراءة؛ لا onboarding ذاتي أو فرض حصص أو checkout أو webhooks أو تجديد أو لوحة مشغل.
- المخزون يشمل الأصناف والمستودعات والاستلام/الصرف والتحويل وتتبع الأرقام التسلسلية وتقرير التقييم التاريخي. كما يربط ترحيل مسودات شراء/بيع محددة بحركات المخزون، ويحسب تكلفة الصرف بمتوسط التكلفة المرجح حتى تاريخ مستند البيع. لا تزال الجردات الفعلية والتسويات والجرد الدوري والمرتجعات والمطابقة الكاملة بين أمر الشراء والاستلام والفاتورة غير مكتملة. واجهة WPF للصناديق والبنوك تدعم سندات الصرف وتخصيصها على فواتير الشراء المرحلة وترحيل GL، لكن لا توجد مطابقة بنكية. VAT المشتريات رقم داخلي ولا يثبت صحة مستند المورد أو قابلية استرداد ضريبة المدخلات.
- لا عملات متعددة أو أسعار صرف؛ القيود تستخدم عملة الشركة الأساسية.
- التقارير المتاحة عبر API تشمل الأستاذ العام وميزان المراجعة وقائمة دخل وميزانية أولية وأعمار الذمم المدينة والدائنة. شاشة أعمار الذمم تقرأ تقارير API الجديدة؛ يلزم اختبار مصالحة مستقل مع الأستاذ العام، بينما التدفقات النقدية والقوائم المالية المعتمدة غير مكتملة.
- لا دليل إنتاجي على نشر/مراقبة/backup وrestore أو توقيع وتحديث تطبيق Windows. زر الطباعة وExcel وPDF معطل عمدًا؛ pagination server-side والتحميل التدريجي وإدارة تبويبات مستندات متعددة لم تُنفذ بعد. البحث الحالي يعمل على السجلات المحمّلة محليًا وليس بحثًا عامًا server-side.
- لا مراجعة محاسبية/ضريبية مستقلة أو اختبار اختراق.

## قيود فنية
- ترحيلات 0001–0012 مطلوبة بالترتيب على قاعدة جديدة، من bootstrap إلى ربط حركات المخزون وسندات التسوية الداخلية. وهي نصوص bootstrap/ترحيلات SQL وليست بعد سلسلة ترقية مُدارة بالكامل؛ اختبر التثبيت النظيف وترقية نسخة موجودة على قاعدة غير إنتاجية قبل التطبيق.
- يلزم ضبط Oidc:Authority/ClientId/Scope وتسجيل callback لدى موفر هوية، وضبط Authentication:Authority/Audience على API وتوفير مستخدم/عضوية تطابق claim sub. تدفق end-session لدى الموفر غير منفذ؛ الخروج الحالي محلي.
- فحص البريد في API هو تحقق شكلي وليس إثبات ملكية.
- دقة subtotal الأساسية أربع منازل، بينما حساب VAT يقرّب كل بند إلى منزلتين وفق سياسة أولية في الحاسبة. يلزم اعتماد سياسة التقريب نهائيًا من محاسب وضريبي قبل الإنتاج.
- نجاح CI لا يثبت اعتماد قانوني أو أداء إنتاجيًا أو جاهزية بيع.

**التصنيف: غير جاهز للبيع.** استخدمه للتطوير والاختبار حتى استيفاء RELEASE-CHECKLIST.


## ضريبة القيمة المضافة
- يمكن حفظ تصنيف VAT والإجماليات الداخلية ثم ترحيل قيد GL متوازن. هذا ليس إصدارًا قانونيًا، ولا توجد XML/QR/توقيع أو إرسال ZATCA.
- تصنيفات المعاينة (StandardRated/ZeroRated/Exempt/OutsideScope) تصنيفات داخلية وليست بديلًا عن رموز وقواعد ZATCA الرسمية. يلزم سبب للتصنيفات غير القياسية ومراجعة المعاملة الضريبية لكل توريد.
- سياسة التقريب (منزلتان عشريتان لكل بند) مبدئية للمعاينة فقط؛ لا تعتبر سياسة ضريبية معتمدة لكل حالات الإصدار.
